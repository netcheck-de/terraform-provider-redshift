# redshift_object_grant (Resource)

Owns the exact explicit privilege set for one local or shared database object and one grantee. Tables and views use
`TABLE`;
functions and procedures name their overload with `arguments`; machine learning models use `MODEL`, and COPY templates
`TEMPLATE`. The `ALL TABLES`, `ALL FUNCTIONS`, and `ALL PROCEDURES` types grant on every object that currently exists
in a schema. See AWS
[GRANT](https://docs.aws.amazon.com/redshift/latest/dg/r_GRANT.html) and
[REVOKE](https://docs.aws.amazon.com/redshift/latest/dg/r_REVOKE.html).

## SQL Statements

```sql
GRANT privilege ON ... TO ...;
REVOKE privilege ON ... FROM ...;
REVOKE GRANT OPTION FOR privilege ON ... FROM ...;
```

Deleting the resource revokes the privileges it owns; see [Reconciliation](#reconciliation) for changes.

## Example Usage

```terraform
resource "redshift_object_grant" "report" {
  database_name = "analytics"
  schema_name   = "reporting"
  object_name   = "daily_summary"
  object_type   = "TABLE"
  grantee       = redshift_group.readers.name
  grantee_type  = "GROUP"
  privileges    = ["SELECT"]
}
```

## Schema

### Required

- `database_name` (String) Database containing the object; local unless `database_type = "shared"`.
- `grantee` (String) Receiving identity name; use `public` with `grantee_type = "PUBLIC"`.
- `grantee_type` (String) `ROLE`, `USER`, `GROUP`, or `PUBLIC`.
- `object_type` (String) `DATABASE`, `SCHEMA`, `TABLE` (including views), `FUNCTION`, `PROCEDURE`, `MODEL` (a machine learning model, whose prediction or inference function is granted through it), `TEMPLATE` (a COPY template), or a snapshot of a schema's current objects: `ALL TABLES`, `ALL FUNCTIONS`, or `ALL PROCEDURES`.
- `privileges` (Set of String) Exact explicit privilege set; updated in place. An empty set revokes owned privileges. `DATABASE`: `CREATE`, `USAGE`, `TEMPORARY`, `ALTER`. `SCHEMA`: `CREATE`, `USAGE`, `ALTER`, `DROP`. `TABLE`: `SELECT`, `INSERT`, `UPDATE`, `DELETE`, `DROP`, `REFERENCES`, `ALTER`, `TRUNCATE`. `FUNCTION`, `PROCEDURE`, `MODEL`, `ALL FUNCTIONS`, and `ALL PROCEDURES`: `EXECUTE`. `TEMPLATE`: `USAGE`, `ALTER`, `DROP`. `ALL TABLES`: `SELECT`, `INSERT`, `UPDATE`, `DELETE`, `DROP`, `REFERENCES`. A snapshot reports only the privileges every current object holds.

### Optional

- `arguments` (String) Comma-separated argument types of a local `FUNCTION` or `PROCEDURE`, such as `INTEGER, VARCHAR`, which select one overload; omit it for a routine without arguments. Shared routine permissions cover every overload of the name, so shared grants must omit this argument. Types are canonicalized and lengths dropped, because Redshift identifies local overloads by type names only.
- `database_type` (String) Set to `shared` for a consumer database created from a datashare; omit for a local database. Shared grants run from the administration database. Shared routines and snapshots require a SQL superuser to prove complete catalog visibility. Routines have name-wide ACLs, so `FUNCTION` and `PROCEDURE` require arguments to be omitted; producer routine kinds distinguish their identities. Shared procedures use the verified FUNCTION ACL syntax, and `ALL PROCEDURES` enumerates current procedure names instead of issuing unsupported native bulk syntax. `ALL FUNCTIONS` covers all shared routine names, including procedures. Object-level access requires WITH PERMISSIONS.
- `grant_option_privileges` (Set of String) Subset of `privileges` that the grantee also holds `WITH GRANT OPTION`, so it can grant them to others. Only a `USER` grantee can hold grant options. Defaults to none. Removing a privilege from this set keeps the privilege and revokes only its grant option; Redshift rejects that while the grantee's own grants depend on it, because the provider never cascades.
- `object_name` (String) Table, view, function, procedure, model, or template name; required for `TABLE`, `FUNCTION`, `PROCEDURE`, `MODEL`, and `TEMPLATE` only.
- `schema_name` (String) Schema containing the object, or whose objects an `ALL …` snapshot covers; required for every type except `DATABASE`.

### Read-Only

- `id` (String) JSON import identity within the configured warehouse; independent of connection method and Data API execution history.

## Functions and Procedures

Redshift overloads routine names, so `arguments` lists the argument types that select one overload, such as
`integer, varchar(10)`. Types are validated and canonicalized (`INT4` becomes `INTEGER`), and lengths are dropped,
because Redshift identifies overloads by type names alone; omit `arguments` for a routine without arguments. The
configured spelling is kept in state and in the import identity. Redshift grants `EXECUTE` on a new function to
`PUBLIC` implicitly; the function catalog reports that grant only once the function's privileges have been changed, so
use [default privileges](https://registry.terraform.io/providers/netcheck-de/redshift/latest/docs/resources/default_privileges)
to stop granting it to future functions.

```terraform
resource "redshift_object_grant" "score" {
  database_name           = "analytics"
  schema_name             = "reporting"
  object_name             = "f_score"
  object_type             = "FUNCTION"
  arguments               = "integer, varchar"
  grantee                 = redshift_user.analyst.name
  grantee_type            = "USER"
  privileges              = ["EXECUTE"]
  grant_option_privileges = ["EXECUTE"]
}

resource "redshift_object_grant" "reporting_tables" {
  database_name = "analytics"
  schema_name   = "reporting"
  object_type   = "ALL TABLES"
  grantee       = redshift_role.readers.name
  grantee_type  = "ROLE"
  privileges    = ["SELECT"]
}
```

## Shared Consumer Databases

Set `database_type = "shared"` for objects of a consumer database created from a datashare. This selector is part of
the JSON identity; omitting it preserves the existing local contract and IDs. Shared grants run from the provider's
administration database, never by connecting to the shared database or consulting database-local privilege views.
Shared routine grants and all shared snapshots require a SQL superuser for every read and mutation: their member
enumeration and function/procedure collision checks must not use permission-filtered catalog data. If this cannot
be proved, refresh reports an error and preserves state instead of inferring that an object is gone.
`DATABASE` and `SCHEMA` support `USAGE` without grant options; `TABLE` supports the table privileges listed above.
`FUNCTION` and `PROCEDURE` support `EXECUTE`, including grant options for users. Shared routine permissions cover
every overload
of a name: a grant using an INTEGER signature is also visible for a VARCHAR overload, and revoking either removes the
name-wide grant. Omit `arguments`; configuring it is rejected so separate overload identities cannot accidentally
manage the same permission. `SVV_REDSHIFT_FUNCTIONS.function_type` distinguishes the producer's function and procedure
names, so `FUNCTION` cannot select a procedure and `PROCEDURE` cannot select a function. Before mutating a single
routine or an `ALL PROCEDURES` snapshot, the provider rejects a name that exists as both kinds: the consumer has one
name-wide ACL, so separate tuples could not own it independently. Use distinct producer names or one `ALL FUNCTIONS`
tuple for the shared namespace instead.

Redshift rejects native consumer `PROCEDURE`/`ALL PROCEDURES` grants and `SHOW GRANTS ON PROCEDURE`. The provider
therefore uses the verified `GRANT/REVOKE EXECUTE ON FUNCTION` and `SHOW GRANTS ON FUNCTION` spelling for a shared
procedure. `ALL PROCEDURES` enumerates current procedure names from the administration database and issues those
name-wide statements once per name; it never issues unsupported native bulk procedure SQL. Shared producer procedures
must already have been included through `GRANT EXECUTE ON PROCEDURE ... TO DATASHARE`.

Object-level permissions require the shared database to have been created `WITH PERMISSIONS`; consumers also need
`USAGE` on its database and schema. Table write privileges additionally require the producer to share write access.
The resource checks the shared database in `SVV_REDSHIFT_DATABASES`, its schema/table in `SVV_ALL_SCHEMAS` and
`SVV_ALL_TABLES`, and routine names in `SVV_REDSHIFT_FUNCTIONS`, then reads exact object grants with three-part
`SHOW GRANTS`. `ALL TABLES` and `ALL FUNCTIONS` use database-qualified schema snapshots from the administration
database. Each refresh lists distinct member names and runs `SHOW GRANTS ON TABLE` or `SHOW GRANTS ON FUNCTION`
per member; this preserves user grant options, which `SHOW GRANTS FOR` omits. Privileges and options are reported
only when every current member holds them. Shared `ALL FUNCTIONS` covers all shared routine names, including producer
procedures, rather than filtering by the producer's routine kind; `ALL PROCEDURES` selects procedure names only.
Empty snapshots are treated as missing. Reconciliation
also revokes undesired supported privileges or options held by only some members, so an executed cleanup cannot leave
partial grants hidden by the intersection. Scoped permissions such as `TABLES`
are not adopted as a `TABLE` grant. Do not overlap the database or schema tuple with `redshift_grant` of the same
recipient, even though its identity uses different fields.

```terraform
# A consumer database created from a datashare WITH PERMISSIONS.
# Grant database and schema USAGE separately before reading this table.
resource "redshift_object_grant" "shared_events" {
  database_name = "shared_analytics"
  database_type = "shared"
  schema_name   = "reporting"
  object_name   = "events"
  object_type   = "TABLE"
  grantee       = "analyst"
  grantee_type  = "USER"
  privileges    = ["SELECT"]
}

# Every overload of the shared function name is one permission tuple.
resource "redshift_object_grant" "shared_function" {
  database_name           = "shared_analytics"
  database_type           = "shared"
  schema_name             = "reporting"
  object_name             = "f_shared_identity"
  object_type             = "FUNCTION"
  grantee                 = "analyst"
  grantee_type            = "USER"
  privileges              = ["EXECUTE"]
  grant_option_privileges = ["EXECUTE"]
}

# Use another recipient to avoid overlapping the individual shared function tuple above.
resource "redshift_object_grant" "shared_functions_snapshot" {
  database_name = "shared_analytics"
  database_type = "shared"
  schema_name   = "reporting"
  object_type   = "ALL FUNCTIONS"
  grantee       = "operators"
  grantee_type  = "ROLE"
  privileges    = ["EXECUTE"]
}

# Shared procedures use FUNCTION ACL SQL internally but keep their producer routine kind in the resource identity.
resource "redshift_object_grant" "shared_procedure" {
  database_name = "shared_analytics"
  database_type = "shared"
  schema_name   = "reporting"
  object_name   = "sp_shared_refresh"
  object_type   = "PROCEDURE"
  grantee       = "procedure_reader"
  grantee_type  = "ROLE"
  privileges    = ["EXECUTE"]
}
```

## Models

`MODEL` grants `EXECUTE` on a trained or external machine learning model, such as a
[`redshift_external_model`](https://registry.terraform.io/providers/netcheck-de/redshift/latest/docs/resources/external_model).
Redshift does not grant the model's prediction or inference function on its own: running the function requires
`EXECUTE` on the model, so grant the model rather than a `FUNCTION`. The statement names the model as
`schema.name` and runs in its database. Existence is checked in `SVV_ML_MODEL_INFO`, which shows a regular user only
the models it owns, so a provider SQL identity that is not a superuser can grant only on its own models; the privileges
are read from `SVV_ML_MODEL_PRIVILEGES` in the model's database. `CREATE MODEL` is a system privilege of
[`redshift_system_grant`](https://registry.terraform.io/providers/netcheck-de/redshift/latest/docs/resources/system_grant).

## Snapshots of a Schema

`ALL TABLES`, `ALL FUNCTIONS`, and `ALL PROCEDURES` use `GRANT … ON ALL … IN SCHEMA`, which grants on the objects that
exist when the statement runs; objects created later are not covered. Refresh reports only the privileges that every
current object of the type holds, so a new object without them shows up as drift and the next apply grants them again.
Tables include views. A schema without objects of the type, such as one that holds only procedures for
`ALL FUNCTIONS`, has nothing to cover and is treated as a missing grant. A privilege carries the grant option only when
every object holds it with the option. Because refresh cannot see grants held on only some objects, every create,
update, and destroy also revokes each privilege outside `privileges` and each grant option outside
`grant_option_privileges` on all current objects, so destroy leaves no partial grant behind.
For current and future objects, use [scoped grants](https://registry.terraform.io/providers/netcheck-de/redshift/latest/docs/resources/grant)
or default privileges instead.

## Grant Options

A `USER` grantee can hold privileges `WITH GRANT OPTION`. `grant_option_privileges` owns which of them carry the option:
it must be a subset of `privileges` and defaults to none, so options granted outside Terraform are revoked while the
privilege itself stays. Groups, roles, and `PUBLIC` cannot hold grant options.

## Lifecycle and Ownership

The resource checks object and grantee existence. Databases, schemas, tables, and templates are read with
`SHOW GRANTS ON` the object, routines with `SVV_FUNCTION_PRIVILEGES`, models with `SVV_ML_MODEL_PRIVILEGES`, and
snapshots with `SVV_RELATION_PRIVILEGES` or `SVV_FUNCTION_PRIVILEGES`, all in the object's local database. Scoped,
inherited, and other grantee grants are independent. Avoid overlapping this resource with `redshift_grant` for the same
explicit schema/database tuple, and a snapshot with single-object grants of the same grantee. Language privileges,
column grants, and Lake Formation IAM grants are out of scope. Shared grants use the separate contract above.

Template existence is checked with `SHOW TEMPLATES FROM SCHEMA ... LIKE 'name'`, whose `_` and `%` wildcards can also
match other templates. When a dropped template's name matches
another one that way, refresh fails at `SHOW GRANTS ON TEMPLATE` instead of removing the grant from state; remove it
with `terraform state rm`.

## Reconciliation

Refresh reads the grantee's privileges and grant options on the object from the catalog; an update reads them again,
runs one `GRANT` or `REVOKE` statement per privilege that differs, starting from what the catalog holds, and re-reads
the catalog to verify the exact sets; every change to the tuple itself replaces the grant.

| Change                                                                    | Result                                                                                                                                                                                                                                                     |
|---------------------------------------------------------------------------|------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------|
| `database_name`, `schema_name`, `object_name`, or `object_type`           | replaces the grant: they name another object, so the old object's privileges are revoked and the new one's granted                                                                                                                                         |
| `database_type` set or removed                                            | replaces the grant: shared and local catalog and connection contracts have distinct identities                                                                                                                                                             |
| `arguments`                                                               | replaces the grant: it selects another overload; a new spelling of the same types, such as `INT4` for `INTEGER`, replaces it too, because the configured spelling is part of the identity                                                                  |
| `grantee` or `grantee_type`                                               | replaces the grant: the grantee is part of the tuple                                                                                                                                                                                                       |
| privilege added to `privileges`                                           | `GRANT ... ON DATABASE`, `ON SCHEMA`, `ON TABLE`, `ON FUNCTION`, `ON PROCEDURE`, `ON MODEL`, or `ON TEMPLATE`; for a snapshot `GRANT ... ON ALL TABLES IN SCHEMA` (or `ALL FUNCTIONS`, `ALL PROCEDURES`), which covers the objects that exist when it runs |
| privilege removed from `privileges`                                       | the matching `REVOKE ... FROM`, which also removes its grant option; for a snapshot `REVOKE ... ON ALL ... IN SCHEMA`, which revokes it from every current object, including grants made by single-object tuples                                           |
| `privileges` set to `[]`                                                  | `REVOKE` for every privilege the grantee holds on the object; the resource stays and owns the empty set                                                                                                                                                    |
| privilege added to `grant_option_privileges`                              | `GRANT ... WITH GRANT OPTION`; a privilege added to both sets at once is granted with the option in one statement                                                                                                                                          |
| privilege removed from `grant_option_privileges`, or the argument removed | `REVOKE GRANT OPTION FOR privilege ON ...`; the privilege stays, and Redshift rejects the statement while grants the user made depend on the option                                                                                                        |

An update revokes before it grants, so a failure part-way never leaves more access than either side: removed
privileges first, then removed grant options, then added privileges, then added grant options. The statements share no
transaction: when one fails, the earlier ones stay applied and the next plan shows what is left. A catalog privilege
outside the object type's list fails the refresh. Planning rejects grant options for groups, roles, and `PUBLIC`, and
options outside `privileges`.

**Drift.** Refresh compares the grantee's catalog rows for the object with the state, and the next plan restores the
configuration with the statements above: a privilege or grant option granted outside Terraform is revoked, and a revoked
one is granted again. Other grantees, scoped permissions, and privileges inherited through roles or groups are ignored.
A snapshot reports a privilege only when every current object of its type holds it: when configured, a privilege that a
new object lacks is granted again on all of them, and when not configured, a privilege that only some objects hold is
not reported as drift; the snapshot revokes it whenever it is created, updated, or destroyed. A missing database,
schema, object, routine overload, model, or grantee removes the grant from state, and so does a snapshot whose schema
holds no objects of its type; the next plan creates it again.

### Replacing Database Privileges

`CREATE` and `TEMPORARY` are revoked before `USAGE` is granted:

```terraform
resource "redshift_object_grant" "readers" {
  database_name = "analytics"
  object_type   = "DATABASE"
  grantee_type  = "GROUP"
  grantee       = "readers"
  privileges    = ["USAGE"] # was ["CREATE", "TEMPORARY"]
}
```

```sql
REVOKE CREATE ON DATABASE "analytics" FROM GROUP "readers";

REVOKE TEMPORARY ON DATABASE "analytics" FROM GROUP "readers";

GRANT USAGE ON DATABASE "analytics" TO GROUP "readers";
```

### Changing Privileges and Grant Options Together

For a user, one change can remove a privilege with its option (`DELETE`), keep a privilege but remove its option
(`SELECT`), add a plain privilege (`TRUNCATE`), add the option to a held privilege (`INSERT`), and add a privilege with
its option (`UPDATE`). The update runs the statements in that order, between its two catalog reads:

```terraform
resource "redshift_object_grant" "orders" {
  database_name = "analytics"
  schema_name   = "serving"
  object_name   = "orders"
  object_type   = "TABLE"
  grantee_type  = "USER"
  grantee       = "analyst"

  privileges              = ["INSERT", "SELECT", "TRUNCATE", "UPDATE"] # was ["DELETE", "INSERT", "SELECT"]
  grant_option_privileges = ["INSERT", "UPDATE"]                       # was ["DELETE", "SELECT"]
}
```

```sql
REVOKE DELETE ON TABLE "analytics"."serving"."orders" FROM "analyst";

REVOKE GRANT OPTION FOR SELECT ON TABLE "analytics"."serving"."orders" FROM "analyst";

GRANT TRUNCATE ON TABLE "analytics"."serving"."orders" TO "analyst";

GRANT INSERT ON TABLE "analytics"."serving"."orders" TO "analyst" WITH GRANT OPTION;

GRANT UPDATE ON TABLE "analytics"."serving"."orders" TO "analyst" WITH GRANT OPTION;
```

## Import

Use an `import` block with a JSON identity:

```terraform
import {
  to = redshift_object_grant.report
  id = jsonencode({
    database_name = "analytics"
    schema_name   = "reporting"
    object_name   = "daily_summary"
    object_type   = "TABLE"
    grantee       = "report_readers"
    grantee_type  = "GROUP"
  })
}
```

Alternatively, use `terraform import`:

```shell
terraform import redshift_object_grant.report \
  '{"database_name":"analytics","schema_name":"reporting","object_name":"daily_summary","object_type":"TABLE","grantee":"report_readers","grantee_type":"GROUP"}'

# Function overload: arguments as configured
terraform import redshift_object_grant.score \
  '{"database_name":"analytics","schema_name":"reporting","object_name":"f_score","object_type":"FUNCTION","arguments":"INTEGER, VARCHAR","grantee":"analyst","grantee_type":"USER"}'
```

For shared consumer objects, include `"database_type":"shared"` in the JSON identity; local identities omit it.

Routine identities add `arguments` as configured.
