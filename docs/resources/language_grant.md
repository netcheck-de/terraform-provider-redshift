# redshift_language_grant (Resource)

Owns `USAGE` on one language in one local database for one grantee. `USAGE ON LANGUAGE sql` is required to create SQL
user-defined functions and `USAGE ON LANGUAGE plpgsql` to create stored procedures. See AWS
[GRANT](https://docs.aws.amazon.com/redshift/latest/dg/r_GRANT.html) and
[REVOKE](https://docs.aws.amazon.com/redshift/latest/dg/r_REVOKE.html).

## SQL Statements

```sql
GRANT USAGE ON LANGUAGE language_name TO ... [WITH GRANT OPTION];
REVOKE [GRANT OPTION FOR] USAGE ON LANGUAGE language_name FROM ...;
```

Deleting the resource revokes what it owns; see [Reconciliation](#reconciliation) for changes.

## Example Usage

```terraform
# Stored procedure authors in the analytics database.
resource "redshift_language_grant" "procedures" {
  database_name = "analytics"
  language_name = "plpgsql"
  grantee       = redshift_role.developers.name
  grantee_type  = "ROLE"
  privileges    = ["USAGE"]
}

# A user who may create SQL UDFs and pass that right on.
resource "redshift_language_grant" "sql_udfs" {
  database_name           = "analytics"
  language_name           = "sql"
  grantee                 = redshift_user.udf_owner.name
  grantee_type            = "USER"
  privileges              = ["USAGE"]
  grant_option_privileges = ["USAGE"]
}

# Only the grantees above may create stored procedures: this revokes the built-in USAGE that PUBLIC holds.
resource "redshift_language_grant" "public_procedures" {
  database_name = "analytics"
  language_name = "plpgsql"
  grantee       = "public"
  grantee_type  = "PUBLIC"
  privileges    = []
}
```

## Schema

### Required

- `database_name` (String) Local database whose language privileges are managed; language privileges are per database. Changing it replaces the grant.
- `grantee` (String) Receiving identity name; use `public` for `PUBLIC`. Changing it replaces the grant.
- `grantee_type` (String) `ROLE`, `USER`, `GROUP`, or `PUBLIC`. Changing it replaces the grant.
- `language_name` (String) `SQL` (SQL user-defined functions) or `PLPGSQL` (stored procedures), in any case; another case of the same language is recorded in place. Changing it replaces the grant.
- `privileges` (Set of String) Exact explicit privilege set. An empty set revokes owned privileges.

### Optional

- `grant_option_privileges` (Set of String) Subset of `privileges` that the grantee also holds `WITH GRANT OPTION`, so it can grant them to others. Only a `USER` grantee can hold grant options. Defaults to none. Removing a privilege from this set keeps the privilege and revokes only its grant option; Redshift rejects that while the grantee's own grants depend on it, because the provider never cascades.

### Read-Only

- `id` (String) JSON import identity; independent of Data API execution history.

## Lifecycle and Ownership

The resource checks the grantee and the local database, then reads
[SVV_LANGUAGE_PRIVILEGES](https://docs.aws.amazon.com/redshift/latest/dg/r_SVV_LANUGAGE_PRIVILEGES.html) in that
database, including `admin_option` for grant options.

Redshift grants `USAGE` on `sql` and `plpgsql` to `PUBLIC` by default, and `SVV_LANGUAGE_PRIVILEGES` lists only
explicit grants, so the default may have no catalog row. To restrict who can create functions or procedures, manage the
`PUBLIC` tuple with an empty `privileges` set and grant `USAGE` to specific users, roles, or groups. Because the
default can be invisible, every create, update, and destroy of a `PUBLIC` tuple without `USAGE` sends
`REVOKE USAGE ON LANGUAGE ... FROM PUBLIC`, which changes nothing once the grant is gone. Importing such a tuple plans
no change, so create it instead of importing it. Destroying any `PUBLIC` tuple leaves `PUBLIC` without `USAGE`; the
default is never restored. To give it back, apply `privileges = ["USAGE"]`, then remove the resource with a `removed`
block whose `lifecycle { destroy = false }` keeps that grant.

## Reconciliation

Refresh reads the grantee's `USAGE` on the language and its grant option from `SVV_LANGUAGE_PRIVILEGES`; an update
reads them again, runs the `GRANT` or `REVOKE` statements for the difference, starting from what the catalog holds, and
re-reads the catalog to verify the result; every change to the tuple itself replaces the grant.

| Change                                                         | Result                                                                                                                                                                                            |
|----------------------------------------------------------------|---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------|
| `database_name` or `language_name`                             | replaces the grant: language privileges are per database and language, so the old tuple's `USAGE` is revoked and the new tuple's granted                                                          |
| `grantee` or `grantee_type`                                    | replaces the grant: the grantee is part of the tuple                                                                                                                                              |
| `privileges` set to `["USAGE"]`                                | `GRANT USAGE ON LANGUAGE ... TO ...`, with `WITH GRANT OPTION` when `grant_option_privileges` is set in the same change                                                                           |
| `privileges` set to `[]`                                       | `REVOKE USAGE ON LANGUAGE ... FROM ...`, which also removes the grant option; for `PUBLIC` also when the catalog shows no grant, as [Lifecycle and Ownership](#lifecycle-and-ownership) describes |
| `grant_option_privileges` set to `["USAGE"]`                   | `GRANT USAGE ON LANGUAGE ... TO ... WITH GRANT OPTION`                                                                                                                                            |
| `grant_option_privileges` set to `[]`, or the argument removed | `REVOKE GRANT OPTION FOR USAGE ON LANGUAGE ... FROM ...`; `USAGE` stays, and Redshift rejects the statement while grants the user made depend on the option                                       |

An update revokes before it grants. The statements share no transaction: when one fails, the earlier ones stay applied
and the next plan shows what is left. Planning rejects grant options for groups, roles, and `PUBLIC`, and an option
without `USAGE` in `privileges`.

**Drift.** Refresh compares the grantee's explicit `USAGE` and grant option with the state, and the next plan restores
the configuration with the statements above: a grant or option added outside Terraform is revoked, and a revoked one is
granted again. The `PUBLIC` default without a catalog row is never read, so a `PUBLIC` tuple without `USAGE` detects
an explicit `GRANT USAGE ... TO PUBLIC` but not the default. A missing grantee or database removes the grant from state,
and the next plan creates it again.

### Revoking the PUBLIC Default

Creating a `PUBLIC` tuple without `USAGE` revokes the default although the catalog read before it shows no grant; the
statements appear with the database each runs in:

```terraform
resource "redshift_language_grant" "public_sql" {
  database_name = "warehouse"
  language_name = "sql"
  grantee_type  = "PUBLIC"
  grantee       = "public"
  privileges    = []
}
```

```sql
-- database: admin
SELECT database_name FROM svv_redshift_databases WHERE database_name = :database AND database_type = 'local';
-- params: {"database":"warehouse"}

-- database: warehouse
SELECT privilege_type, admin_option FROM svv_language_privileges WHERE language_name = :language AND identity_name = :grantee AND identity_type = :identity_type;
-- params: {"grantee":"public","identity_type":"public","language":"sql"}

-- database: warehouse
REVOKE USAGE ON LANGUAGE SQL FROM PUBLIC;
-- params: {}

-- database: admin
SELECT database_name FROM svv_redshift_databases WHERE database_name = :database AND database_type = 'local';
-- params: {"database":"warehouse"}

-- database: warehouse
SELECT privilege_type, admin_option FROM svv_language_privileges WHERE language_name = :language AND identity_name = :grantee AND identity_type = :identity_type;
-- params: {"grantee":"public","identity_type":"public","language":"sql"}
```

## Import

In Terraform 1.5 and later, use an `import` block with a JSON identity:

```terraform
import {
  to = redshift_language_grant.procedures
  id = jsonencode({
    workgroup_name = "warehouse"
    database       = "admin"
    database_name  = "analytics"
    language_name  = "plpgsql"
    grantee        = "developers"
    grantee_type   = "ROLE"
  })
}
```

The example binds a Serverless workgroup. Replace `workgroup_name` with `cluster_identifier` for a provisioned
cluster, or with `endpoint` (`host:port`) for a direct password connection; see
[connection methods](../guides/connection_methods.md#imports-and-transport-switching).

Alternatively, use `terraform import`:

```shell
terraform import redshift_language_grant.procedures \
  '{"workgroup_name":"warehouse","database":"admin","database_name":"analytics","language_name":"plpgsql","grantee":"developers","grantee_type":"ROLE"}'
```
