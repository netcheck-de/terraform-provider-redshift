# redshift_database (Resource)

Creates a local database with an optional owner, connection limit, collation, and isolation level, the destination
database of an **active** zero-ETL integration, or a consumer database from an **already associated** producer
datashare. Datashare authorization and the namespace-scoped consumer association are AWS resources and must precede
shared database creation. The provider waits for the inbound share to appear in the SQL catalog, for up to five minutes
or, when set, the `timeouts.create` duration. See AWS
[CREATE DATABASE](https://docs.aws.amazon.com/redshift/latest/dg/r_CREATE_DATABASE.html) and
[ALTER DATABASE](https://docs.aws.amazon.com/redshift/latest/dg/r_ALTER_DATABASE.html).

## SQL Statements

```sql
CREATE DATABASE name ...;
ALTER DATABASE name ...;
DROP DATABASE name;
```

## Example Usage

```terraform
resource "redshift_database" "analytics" {
  name          = "analytics"
  datashare_arn = aws_redshift_data_share_consumer_association.analytics.data_share_arn

  # Wait up to 15 minutes, instead of 5, for the associated share to appear in the SQL catalog.
  timeouts {
    create = "15m"
  }
}

resource "redshift_database" "local" {
  name             = "warehouse"
  owner            = "etl"
  connection_limit = 50
  # On an empty database, changing this runs ALTER in place; existing user tables make Redshift reject it safely.
  collation       = "CASE_INSENSITIVE"
  isolation_level = "SNAPSHOT"
}

# The read-only destination of an active zero-ETL integration. The warehouse must set enable_case_sensitive_identifier.
resource "redshift_database" "replica" {
  name = "orders_replica"

  integration {
    integration_id   = "a1b2c3d4-5678-90ab-cdef-example11111"
    source_database  = "orders"
    refresh_interval = 600
    query_all_states = true
  }
}

# DynamoDB uses aws_redshift_integration, not aws_rds_integration. Its source needs PITR and an export resource policy.
resource "redshift_database" "dynamodb_replica" {
  name = "dynamodb_replica"

  integration {
    integration_id   = "b2c3d4e5-6789-01ab-cdef-example22222"
    refresh_interval = 900
    # DynamoDB sources do not take source_database.
  }
}
```

## Schema

### Required

- `name` (String) Database name.

### Optional

- `collation` (String) `CASE_SENSITIVE` (the Redshift default) or `CASE_INSENSITIVE` string comparison for a local database. Changed in place with `ALTER DATABASE ... COLLATE`; Redshift may reject the change when database objects exist, without replacing the database. A change strictly reads `DB_COLLATION()` in fresh sessions before and immediately after COLLATE, before changing other options. Verified partial progress is saved if later work fails. Refresh also reads collation; a refused session warns and keeps the last known value. Omit it to keep the current collation. Not supported for shared or integration databases.
- `connection_limit` (Number) Maximum number of concurrent connections to a local database; `-1` means `UNLIMITED`, the Redshift default. Superusers are exempt. Updated in place with `ALTER DATABASE ... CONNECTION LIMIT`. Omit it to keep and report the current limit. Not supported for shared databases, where it is null.
- `datashare_arn` (String) Producer datashare ARN. Omit for a local database; associate the share through AWS before creating a consumer database.
- `integration` (Block, Optional) Creates the database as the read-only destination of an active zero-ETL integration with `CREATE DATABASE ... FROM INTEGRATION`, which needs a superuser or a user with `CREATEDB` and `CREATEUSER`; replication runs with that user's permissions. The warehouse must set `enable_case_sensitive_identifier`. Conflicts with `datashare_arn` and `collation`. Refresh reads `SVV_INTEGRATION`, which only superusers can see. - `owner` (String) SQL user owning a local database. Set with `OWNER` at creation and changed in place with `ALTER DATABASE ... OWNER TO`, which requires a superuser. Omit it to keep and report the current owner. Not supported for shared databases, where it is null.

## Local Database Options

`owner`, `connection_limit`, `collation`, and `isolation_level` apply to local databases only; configuring any of them
together with `datashare_arn` is rejected at plan time, and they are null for shared databases. Omitted options are
reported from the catalog and left unmanaged; see [Reconciliation](#reconciliation) for how changes apply.

| Attribute          | Created with       | Changed with                              | Read from                                   |
|--------------------|--------------------|-------------------------------------------|---------------------------------------------|
| `owner`            | `OWNER`            | `ALTER DATABASE ... OWNER TO` (superuser) | `PG_DATABASE_INFO.datdba`                   |
| `connection_limit` | `CONNECTION LIMIT` | `ALTER DATABASE ... CONNECTION LIMIT`     | `PG_DATABASE_INFO.datconnlimit`             |
| `collation`        | `COLLATE`          | `ALTER DATABASE ... COLLATE`              | `DB_COLLATION()` inside the database        |
| `isolation_level`  | `ISOLATION LEVEL`  | `ALTER DATABASE ... ISOLATION LEVEL`      | `SHOW DATABASES` `database_isolation_level` |

`connection_limit = -1` renders `UNLIMITED`; superusers are not limited. The isolation level of the `dev` database
cannot be changed. Changes apply to new sessions.

## Zero-ETL Integration Databases

The `integration` block creates the database with `CREATE DATABASE ... FROM INTEGRATION`, the read-only destination of
a zero-ETL integration from Aurora, RDS, DynamoDB, or another supported source. The integration is an AWS resource,
such as `aws_rds_integration`, and must be active first. The warehouse must set `enable_case_sensitive_identifier`, and
creating the database needs a superuser or a user with `CREATEDB` and `CREATEUSER`, whose permissions replication then
uses. `integration_id` is the identifier `SVV_INTEGRATION` reports. Aurora PostgreSQL, RDS for PostgreSQL, and RDS for
Oracle sources also need `source_database`. The block conflicts with `datashare_arn` and `collation`; `owner`,
`connection_limit`, and `isolation_level` apply as for a local database.

| Attribute                          | Created with       | Changed with                         | Read from                          |
|------------------------------------|--------------------|--------------------------------------|------------------------------------|
| `integration.integration_id`       | `FROM INTEGRATION` | replacement                          | `SVV_INTEGRATION.integration_id`   |
| `integration.source_database`      | `DATABASE`         | replacement                          | `SVV_INTEGRATION.source_database`  |
| `integration.refresh_interval`     | `REFRESH_INTERVAL` | `ALTER DATABASE ... INTEGRATION SET` | `SVV_INTEGRATION.refresh_interval` |
| `integration.history_mode`         | `HISTORY_MODE`     | `ALTER DATABASE ... INTEGRATION SET` | `SVV_INTEGRATION.is_history_mode`  |
| `integration.auto_remediation`     | `AUTO_REMEDIATION` | `ALTER DATABASE ... INTEGRATION SET` | `SVV_INTEGRATION.auto_remediation` |
| `integration.query_all_states`     | `QUERY_ALL_STATES` | `ALTER DATABASE ... INTEGRATION SET` | not read back                      |
| `integration.accept_invalid_chars` | `ACCEPTINVCHARS`   | `ALTER DATABASE ... INTEGRATION SET` | not read back                      |
| `integration.truncate_columns`     | `TRUNCATECOLUMNS`  | `ALTER DATABASE ... INTEGRATION SET` | not read back                      |

`SVV_INTEGRATION` is visible only to superusers, so the provider identity managing a destination database must be one.
`refresh_interval` accepts 0 to 432000 seconds; DynamoDB sources need at least 900. Turning `history_mode` on or off
switches only tables in the `Synced` state. The provider does not run `ALTER DATABASE ... INTEGRATION REFRESH` or set
history mode for single tables. A destination database reports no collation, and its `database_type` is the type
`SHOW DATABASES` reports for it.

`SVV_INTEGRATION` can lag behind an acknowledged change. Create and Update poll readable integration settings for
up to one minute, or a shorter configured operation timeout, before reporting a convergence failure. A non-superuser
gets a permission error from this view; managing an integration therefore requires a superuser throughout its lifecycle.
During apply verification, temporarily absent rows are retried without clearing the expected integration binding,
including when visibility times out. Ordinary refresh still handles a missing integration as deletion.
An in-place history-mode change adds `FOR ALL TABLES`: without it, Redshift changes only the default for newly
replicated tables. Existing tables must be `Synced` to switch mode, and switching can start a table resynchronization.

For DynamoDB, use `aws_redshift_integration` instead of `aws_rds_integration`, omit `source_database`, and set
`refresh_interval` to at least 900 seconds. The source table needs point-in-time recovery and a resource policy
authorizing Redshift exports. The [complete example](https://github.com/netcheck-de/terraform-provider-redshift/tree/main/examples/complete)
supports an existing table ARN in `zero_etl_source_arn` or a disposable table with `zero_etl_create_dynamodb_source = true`.

## Lifecycle and Ownership

Deletion drops only the matching database, without `CASCADE`; active sessions or grants may prevent it.

Redshift refuses to drop a zero-ETL destination while its integration is active, also with `FORCE`. Because the
destination depends on the integration's ID, Terraform destroys the database first, also under `-target`, and the
destroy fails with an error that says so. Delete the integration outside Terraform, for example with
`aws rds delete-integration` for Aurora/RDS or `aws redshift delete-integration` for DynamoDB, wait until it is gone,
and destroy again: the refresh then drops the integration from
state, and the database, which stays behind as a local database, is dropped. This resource
manages no `PUBLIC` grants; assign permissions separately. The data source reports the permission mode of a local
database as `false`. Resource refreshes do not require AWS datashare discovery permissions.

## Timeouts

The `timeouts` block limits a whole create, update, or delete: every statement it runs and the catalog reads before
and after. For a shared database, `create` also bounds the wait for the associated datashare to appear in the SQL
catalog, which polls every second and otherwise gives up after five minutes; raise it when a fresh association takes
longer to arrive. Without the block, an operation has no limit of its own besides that wait, and each statement is
bounded only by the provider's `query_timeout`. With it, a statement still running when the operation's time is up is
cancelled, even when its `query_timeout` is later, and the apply fails with an `Operation timed out` error.

```terraform
timeouts {
  create = "15m"
}
```

Values are durations such as `90s`, `30m`, or `2h`. A `delete` value applies only after an apply has saved it to
state. Refreshes are bounded only by `query_timeout`. A change to the values alone is an in-place update; see
[Reconciliation](#reconciliation).

## Reconciliation

Refresh reads the database from `SHOW DATABASES`, for a local or zero-ETL destination database its owner and
connection limit from `PG_DATABASE_INFO`, and for a destination its integration from `SVV_INTEGRATION`; an update reads
them again, runs one `ALTER DATABASE` statement per changed local option and one `ALTER DATABASE ... INTEGRATION SET`
per changed integration setting, starting from what the catalog holds, and re-reads the catalog to verify the result;
every other change replaces the database with `DROP DATABASE` and `CREATE DATABASE`, which **drops everything stored in
a local database** and starts the replication of a destination over. Protect databases that hold data:

```terraform
lifecycle {
  prevent_destroy = true
}
```

| Change                                                     | Result                                                                                                                                                                 |
|------------------------------------------------------------|------------------------------------------------------------------------------------------------------------------------------------------------------------------------|
| `name`                                                     | replaces the database: the provider never renames a database                                                                                                           |
| `datashare_arn` set, changed, or removed                   | replaces the database: a local database cannot become a consumer database, and a consumer database cannot be bound to another datashare                                |
| `with_permissions` of a shared database                    | replaces the database: `WITH PERMISSIONS` is part of `CREATE DATABASE ... FROM DATASHARE` only                                                                         |
| `with_permissions` of a local database                     | no SQL; the configured value is recorded and has no effect                                                                                                             |
| `owner` set or changed                                     | `ALTER DATABASE ... OWNER TO`, which requires a superuser                                                                                                              |
| `owner` removed                                            | no SQL; the current owner stays and is still reported                                                                                                                  |
| `connection_limit` set or changed                          | `ALTER DATABASE ... CONNECTION LIMIT`, with `UNLIMITED` for `-1`                                                                                                       |
| `connection_limit` removed                                 | no SQL; the current limit stays and is still reported                                                                                                                  |
| `collation` set to a value other than the one in state     | alters in place inside the database; restrictions fail safely without replacement; see below                                                                           |
| `collation` set while the state holds none                 | reads, alters if different, and verifies in fresh sessions; refused connections fail the update; see below                                                             |
| `collation` removed                                        | no SQL; the database keeps its collation                                                                                                                               |
| `isolation_level` set or changed                           | `ALTER DATABASE ... ISOLATION LEVEL`, which fails while other sessions are connected to the database                                                                   |
| `isolation_level` removed                                  | no SQL; the current level stays and is still reported                                                                                                                  |
| `integration` block added or removed                       | replaces the database: a local database cannot become a zero-ETL destination, nor a destination a local database                                                       |
| `integration.integration_id` changed                       | replaces the database, also when the value is known only at apply: a destination is bound to its integration at creation                                               |
| `integration.source_database` set or changed               | replaces the database: the source database is part of `CREATE DATABASE ... FROM INTEGRATION` only                                                                      |
| `integration.source_database` removed                      | no SQL; the source database stays and is still reported                                                                                                                |
| `integration.refresh_interval` set or changed              | `ALTER DATABASE ... INTEGRATION SET REFRESH_INTERVAL`                                                                                                                  |
| `integration.refresh_interval` removed                     | no SQL; the current interval stays and is still reported                                                                                                               |
| `integration.history_mode` set or changed                  | `ALTER DATABASE ... INTEGRATION SET HISTORY_MODE`, which switches only tables in the `Synced` state                                                                    |
| `integration.history_mode` removed                         | no SQL; the current setting stays and is still reported                                                                                                                |
| `integration.auto_remediation` set or changed              | `ALTER DATABASE ... INTEGRATION SET AUTO_REMEDIATION`                                                                                                                  |
| `integration.auto_remediation` removed                     | no SQL; the current setting stays and is still reported                                                                                                                |
| `integration.query_all_states` set or changed              | `ALTER DATABASE ... INTEGRATION SET QUERY_ALL_STATES`                                                                                                                  |
| `integration.accept_invalid_chars` set or changed          | `ALTER DATABASE ... INTEGRATION SET ACCEPTINVCHARS`                                                                                                                    |
| `integration.truncate_columns` set or changed              | `ALTER DATABASE ... INTEGRATION SET TRUNCATECOLUMNS`                                                                                                                   |
| `integration.query_all_states` removed                     | no SQL; the setting stays as it is and is no longer managed                                                                                                            |
| `integration.accept_invalid_chars` removed                 | no SQL; the setting stays as it is and is no longer managed                                                                                                            |
| `integration.truncate_columns` removed                     | no SQL; the setting stays as it is and is no longer managed                                                                                                            |
| `timeouts.create`, `timeouts.update`, or `timeouts.delete` | no DDL of its own, but an in-place update that re-reads and verifies the catalog: it moves options changed outside Terraform since the plan back to the planned values |

Collation changes require a session inside the database being altered. Redshift accepts the change for an empty
database, but rejects it when a user-created table exists. The provider lets Redshift check eligibility instead of
inferring it from visible tables, and never replaces a database as a fallback. Resolve the restriction or keep the
existing collation; an explicit `terraform apply -replace` is destructive and remains the operator's choice.
Both the pre-update read and the post-update verification use fresh sessions and `DB_COLLATION()`. If a connection
limit refuses either session, the update fails rather than treating the planned value as verified. Allow a session
by raising the limit or using a superuser, then refresh and retry. Verification happens immediately after `COLLATE`,
before another statement can close the target database with a connection limit. Verified partial progress remains
in state even when a later statement or catalog read fails. Other updates do not open a collation session.
The complete example's deliberately empty `example_collation_probe` database demonstrates this migration with
`database_collation_insensitive = true` and reports its observed value in `database_collation_migration`.

An update runs its statements in the order collation, owner, connection limit, isolation level, then the integration
settings in the order of the `CREATE DATABASE` syntax. They share no transaction: when one fails, the earlier ones stay
applied and the next plan shows what is left. After them, the update fails when the catalog does not hold every
configured option it reports, or when a shared database no longer has the planned `with_permissions`. Changing every
integration setting of a destination database:

```terraform
integration {
  integration_id       = "a1b2c3d4-5678-90ab-cdef-example11111"
  refresh_interval     = 0     # was 600
  history_mode         = false # was true
  auto_remediation     = false # was true
  query_all_states     = false # was true
  accept_invalid_chars = true  # was false
  truncate_columns     = false # was true
}
```

runs one statement per setting:

```sql
ALTER DATABASE "replica" INTEGRATION SET ACCEPTINVCHARS = TRUE;

ALTER DATABASE "replica" INTEGRATION SET QUERY_ALL_STATES = FALSE;

ALTER DATABASE "replica" INTEGRATION SET REFRESH_INTERVAL 0;

ALTER DATABASE "replica" INTEGRATION SET TRUNCATECOLUMNS = FALSE;

ALTER DATABASE "replica" INTEGRATION SET HISTORY_MODE = FALSE FOR ALL TABLES;

ALTER DATABASE "replica" INTEGRATION SET AUTO_REMEDIATION = FALSE;
```

**Drift.** Refresh compares the owner, connection limit, and isolation level of a local database, and `with_permissions`
of a shared database, with the state. A configured local option changed outside Terraform is set back with the
statements above; an omitted one follows the catalog and never plans a change. A shared database whose permission mode
differs from the configuration is replaced. A database dropped outside Terraform is removed from state, and the next
plan creates it again. A database that changed between local and shared, or is bound to another producer share than
`datashare_arn` names, fails the refresh instead of planning a change. Refresh re-reads `collation` in a fresh session;
when that session is refused, a warning preserves the last known value instead of blocking refresh. A later successful
refresh recovers the actual collation, including changes made before a failed update. For a zero-ETL destination,
refresh compares
`source_database`, `refresh_interval`, `history_mode`, and `auto_remediation` with `SVV_INTEGRATION`: a configured
setting changed outside Terraform is set back, an omitted one follows the catalog, and a changed source database
replaces the database. `query_all_states`, `accept_invalid_chars`, and `truncate_columns` are never read back, so
changes to them outside Terraform are not detected. A destination that `SVV_INTEGRATION` no longer shows, because the
integration was deleted, keeps its database: the refresh warns and
drops the `integration` block from state, so the next plan replaces the database, and a destroy still drops it. A
destination that receives another integration than `integration_id` names, or that became a shared database, fails the
refresh, as does a destination configured without the `integration` block. Comments, grants, and the objects inside the
database are never read.
If the provider identity loses superuser catalog access, refresh fails with the permission error instead of removing
the integration binding from state.

## Import

Use an `import` block with a JSON identity:

```terraform
import {
  to = redshift_database.analytics
  id = jsonencode({
    workgroup_name = "warehouse"
    database       = "admin"
    name           = "analytics"
    datashare_arn  = "arn:aws:redshift:eu-central-1:123456789012:datashare:11111111-2222-3333-4444-555555555555/source"
  })
}
```

The example binds a Serverless workgroup. Replace `workgroup_name` with `cluster_identifier` for a provisioned
cluster, or with `endpoint` (`host:port`) for a direct password connection; see
[connection methods](../guides/connection_methods.md#imports-and-transport-switching).

Alternatively, use `terraform import`:

```shell
terraform import redshift_database.analytics \
  '{"workgroup_name":"warehouse","database":"admin","name":"analytics","datashare_arn":"arn:aws:redshift:eu-central-1:123456789012:datashare:11111111-2222-3333-4444-555555555555/source"}'
```

For a local database, omit `datashare_arn` and `integration_id` from the import ID. For a shared database
`datashare_arn` must match the existing producer binding. For a zero-ETL destination, replace `datashare_arn` with
`integration_id`, the integration the database receives as `SVV_INTEGRATION` reports it. `with_permissions`, the local
database options, and the integration settings `SVV_INTEGRATION` reports are discovered on refresh;
`query_all_states`, `accept_invalid_chars`, and `truncate_columns` stay unmanaged until configured.
