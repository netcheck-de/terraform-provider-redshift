# redshift_masking_policy (Resource)

Manages one dynamic data masking policy: its typed input columns and the expression that computes the masked value.
Attach it to columns with `redshift_masking_policy_attachment`, and give it access to lookup tables with
`redshift_policy_grant`. See AWS
[CREATE MASKING POLICY](https://docs.aws.amazon.com/redshift/latest/dg/r_CREATE_MASKING_POLICY.html) and
[Dynamic data masking](https://docs.aws.amazon.com/redshift/latest/dg/t_ddm.html).

## SQL Statements

```sql
CREATE MASKING POLICY name WITH (...) USING (expression);
ALTER MASKING POLICY name USING (expression);
DROP MASKING POLICY name;
```

## Example Usage

```terraform
resource "redshift_masking_policy" "email" {
  database   = redshift_database.warehouse.name
  name       = "mask_email"
  expression = "REGEXP_REPLACE(email, '^[^@]+', '***')"

  input_column {
    name = "email"
    type = "VARCHAR(256)"
  }
}

# A conditional policy reads a second column, which the attachment maps through input_columns.
resource "redshift_masking_policy" "card" {
  database   = redshift_database.warehouse.name
  name       = "mask_card"
  expression = "CASE WHEN is_fraud THEN pan ELSE NULL END"

  input_column {
    name = "is_fraud"
    type = "BOOLEAN"
  }

  input_column {
    name = "pan"
    type = "VARCHAR(16)"
  }
}
```

## Schema

### Required

- `database` (String) Local database that holds the policy; the policy can only be attached to relations in this database. Changing it replaces the policy.
- `expression` (String) SQL expression of the `USING` clause that computes the masked value from the input columns, for example `'XXXX'::VARCHAR(256)` or a `CASE` over the inputs. A constant must be cast to the input type. Updated in place with `ALTER MASKING POLICY`. Redshift stores its own rendering, so refresh keeps the configured text while `definition_fingerprint` matches and shows the catalog text after a change made outside Terraform.
- `name` (String) Policy name, unique among the masking policies of the database. Changing it replaces the policy.

### Optional

- `input_column` (Block List) At least one `input_column` block is required. Ordered input columns of the `WITH` clause that the expression reads. Their types must match the masked columns' types when the policy is attached. Redshift cannot alter them, so changing a name or type replaces the policy; another spelling of the same type, such as `TEXT` for `VARCHAR(256)`, does not. (see [below for nested schema](#nestedblock--input_column))

### Read-Only

- `definition_fingerprint` (String) SHA-256 of the catalog definition with whitespace collapsed; detects definition changes made outside Terraform.
- `id` (String) JSON import identity; independent of Data API execution history.

### Nested Schema for `input_column`

Required:

- `name` (String) Input column name used in `expression`; it does not have to match the masked column's name.
- `type` (String) Redshift data type, such as `VARCHAR(256)` or `INTEGER`. A type without length gets the length a column would get, so `VARCHAR` means `VARCHAR(256)`.

## Lifecycle and Ownership

The provider must connect as a superuser or a member of `sys:secadmin`, the only identities that can create masking
policies and read `SVV_MASKING_POLICY`. Statements run in `database`, so the policy name stays unqualified.

Deletion never cascades, and Redshift refuses to drop a policy that is still attached. Referencing the policy from its
attachments makes Terraform detach them first when everything is destroyed.

A type without length gets the length Redshift gives a column, so `VARCHAR` means `VARCHAR(256)`. The routine
pseudo-types `ANYELEMENT` and `REFCURSOR` are rejected, because no column has them.

## Reconciliation

Refresh reads the policy from `SVV_MASKING_POLICY`; an update runs `ALTER MASKING POLICY ... USING` for a new
expression, which keeps the policy's attachments, and re-reads the catalog to verify the result; every other change
replaces the policy; a change to `input_column` replaces it under the same name, because `ALTER MASKING POLICY` cannot
change the input columns or their types.

| Change                                                                                                                                         | Result                                                            |
|------------------------------------------------------------------------------------------------------------------------------------------------|-------------------------------------------------------------------|
| `database` or `name`                                                                                                                           | replaces the policy: the provider never moves or renames a policy |
| `input_column` block added, removed, or reordered                                                                                              | replaces the policy                                               |
| `input_column.name` changed only in case, or `input_column.type` changed to an equivalent type, such as `TEXT` or `VARCHAR` for `VARCHAR(256)` | no SQL; an in-place update records the configured spelling        |
| `input_column.name` or `input_column.type`, any other change                                                                                   | replaces the policy                                               |
| `input_column` known only during apply                                                                                                         | replaces the policy                                               |
| `expression`                                                                                                                                   | `ALTER MASKING POLICY ... USING`                                  |

A replacement keeps the policy name, so the attachments' references to it do not change, and Redshift refuses to drop
the policy while they stay attached. Give every attachment `replace_triggered_by` on the policy's `input_column`, as in
the `redshift_masking_policy_attachment` example: Terraform then detaches the attachments, replaces the policy, and
attaches them again. A switch between equivalent input types also updates `input_column` and so re-creates the
attachments.

**Drift.** Refresh compares the catalog input columns and expression with the state. Redshift stores the expression in
its own rendering, for example with the input columns qualified, so state keeps the configured `expression` while the
catalog text still matches `definition_fingerprint`, the hash recorded at apply time. An expression changed outside
Terraform appears as the catalog text, and the next plan restores the configured one with `ALTER MASKING POLICY`.
Equivalent input types do not count as drift. Input columns that differ from the catalog beyond spelling, as after the
policy was re-created outside Terraform, are stored as the catalog reports them, and the next plan replaces the
policy. A dropped policy is removed from state, and the next plan creates it again.

## Import

In Terraform 1.5 and later, use an `import` block with a JSON identity:

```terraform
import {
  to = redshift_masking_policy.email
  id = jsonencode({
    workgroup_name = "warehouse"
    database       = "warehouse"
    name           = "mask_email"
  })
}
```

Alternatively, use `terraform import`:

```shell
terraform import redshift_masking_policy.email \
  '{"workgroup_name":"warehouse","database":"warehouse","name":"mask_email"}'
```

Import reads the `input_column` blocks and `expression` from the catalog in Redshift's spelling, for example
`character varying(256)`. The first plan therefore shows an in-place update of `expression` unless the configuration
repeats the catalog text, and of `input_column` when the configuration spells an input type differently; neither
replaces the policy, and only the `expression` update runs `ALTER MASKING POLICY`.
