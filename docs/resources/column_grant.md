# redshift_column_grant (Resource)

Owns the exact column-level privileges of one grantee on one table, view, or materialized view: which columns hold
`SELECT` and which hold `UPDATE`. See AWS [GRANT](https://docs.aws.amazon.com/redshift/latest/dg/r_GRANT.html#grant-column-level)
and [REVOKE](https://docs.aws.amazon.com/redshift/latest/dg/r_REVOKE.html#revoke-column-level).

```sql
GRANT privilege (column, ...) ON TABLE database_name.schema_name.object_name TO ...;
REVOKE privilege (column, ...) ON TABLE database_name.schema_name.object_name FROM ...;
```

Deleting the resource revokes the column privileges it owns; see [Reconciliation](#reconciliation) for changes.

## Example Usage

```terraform
resource "redshift_column_grant" "events" {
  database_name = "analytics"
  schema_name   = "reporting"
  object_name   = "events"
  grantee       = redshift_role.analysts.name
  grantee_type  = "ROLE"
  privileges = {
    SELECT = ["id", "label", "created_at"]
    UPDATE = ["label"]
  }
}
```

## Schema

### Required

- `database_name` (String) Local database containing the table or view. Changing it replaces the grant.
- `grantee` (String) Receiving identity name; use `public` for `PUBLIC`. Changing it replaces the grant.
- `grantee_type` (String) `ROLE`, `USER`, `GROUP`, or `PUBLIC`. Changing it replaces the grant.
- `object_name` (String) Table, view, or materialized view whose columns are granted; late-binding views do not support column privileges. Changing it replaces the grant.
- `privileges` (Map of Set of String) Exact explicit column privileges: a map from `SELECT` or `UPDATE` to the set of column names that hold it. Views accept only `SELECT`. Column names are quoted; write them as the catalog stores them, which is lower case unless `enable_case_sensitive_identifier` is on. An empty map revokes every column privilege of this tuple; updated in place.
- `schema_name` (String) Schema containing the table or view. Changing it replaces the grant.

### Read-Only

- `id` (String) JSON import identity; independent of Data API execution history.

One resource owns all columns of one grantee on one relation, because `SVV_COLUMN_PRIVILEGES` reports each column,
privilege, and grantee exactly. Column names are quoted identifiers, so write them as the catalog stores them (lower
case unless case-sensitive identifiers are enabled).

## Lifecycle and Ownership

The resource checks that the grantee, the local database, and the relation exist, then reads
[SVV_COLUMN_PRIVILEGES](https://docs.aws.amazon.com/redshift/latest/dg/r_SVV_COLUMN_PRIVILEGES.html) in that database.

Redshift's [column-level usage notes](https://docs.aws.amazon.com/redshift/latest/dg/r_GRANT-usage-notes.html#r_GRANT-usage-notes-clp)
apply:

- Only the table owner or a superuser can grant column privileges, and `WITH GRANT OPTION` is not supported, so the
  resource has no `grant_option_privileges`.
- Views accept only `SELECT`; late-binding views do not support column privileges.
- A grantee cannot hold the same privilege at table and column level. While a table-level grant (for example from
  `redshift_object_grant`) exists, a column grant has no effect and the resource reports that it did not converge.
  Revoking the privilege at table level also revokes its column grants, which the next refresh shows as drift.

## Reconciliation

Refresh reads the grantee's column privileges on the relation from `SVV_COLUMN_PRIVILEGES`; an update reads them again,
runs at most one `REVOKE` and one `GRANT` per privilege, each listing every column that changes, starting from what the
catalog holds, and re-reads the catalog to verify the exact columns; every change to the tuple itself replaces the
grant.

| Change                                                                       | Result                                                                                                                        |
|------------------------------------------------------------------------------|-------------------------------------------------------------------------------------------------------------------------------|
| `database_name`, `schema_name`, or `object_name`                             | replaces the grant: they name another relation, so the old relation's column privileges are revoked and the new one's granted |
| `grantee` or `grantee_type`                                                  | replaces the grant: the grantee is part of the tuple                                                                          |
| column added to the `SELECT` or `UPDATE` set of `privileges`, or a key added | `GRANT SELECT (column, ...) ON TABLE ... TO ...` or `GRANT UPDATE (...)` with the added columns                               |
| column removed from a set, or a key removed                                  | `REVOKE SELECT (column, ...) ON TABLE ... FROM ...` or `REVOKE UPDATE (...)` with the removed columns                         |
| `privileges` set to `{}`                                                     | `REVOKE` of every column privilege of the tuple; the resource stays and owns the empty map                                    |
| a key with an empty set                                                      | rejected during planning: remove the key to revoke the privilege                                                              |
| columns reordered within a set                                               | no change: the columns form a set                                                                                             |

An update runs every `REVOKE` before any `GRANT`, `SELECT` before `UPDATE`, so a failure part-way never leaves more
access than either side. The statements share no transaction: when one fails, the earlier ones stay applied and the
next plan shows what is left. A catalog column privilege other than `SELECT` or `UPDATE` fails the refresh.

**Drift.** Refresh compares the grantee's column privileges on the relation with the state, and the next plan restores
the configuration with the statements above: a column granted outside Terraform is revoked, and a revoked one is granted
again. Other grantees and other relations are never read. When the catalog does not match after a create or update,
for example under a table-level grant or because Redshift folded a column name to lower case, the apply fails and names
both column sets. A missing grantee, database, or relation removes the grant from state, and the next plan creates it
again.

### Moving Columns Between Privileges

`id` loses `SELECT`, `label` loses `UPDATE` but keeps `SELECT`, and `note` gains both; the revokes run first:

```terraform
resource "redshift_column_grant" "readers" {
  database_name = "warehouse"
  schema_name   = "serving"
  object_name   = "events"
  grantee_type  = "ROLE"
  grantee       = "example:readers"

  privileges = {
    SELECT = ["label", "note"] # was ["id", "label"]
    UPDATE = ["note"]          # was ["label"]
  }
}
```

```sql
SELECT role_name FROM svv_roles WHERE role_name = :name;

SELECT database_name FROM svv_redshift_databases WHERE database_name = :database AND database_type = 'local';

SELECT table_name FROM svv_all_tables WHERE database_name = :database AND schema_name = :schema AND table_name = :name;

SELECT column_name, privilege_type FROM svv_column_privileges WHERE namespace_name = :schema AND relation_name = :object AND identity_name = :grantee AND identity_type = :identity_type ORDER BY privilege_type, column_name;

REVOKE SELECT ("id") ON TABLE "warehouse"."serving"."events" FROM ROLE "example:readers";

REVOKE UPDATE ("label") ON TABLE "warehouse"."serving"."events" FROM ROLE "example:readers";

GRANT SELECT ("note") ON TABLE "warehouse"."serving"."events" TO ROLE "example:readers";

GRANT UPDATE ("note") ON TABLE "warehouse"."serving"."events" TO ROLE "example:readers";
```

## Import

In Terraform 1.5 and later, use an `import` block with a JSON identity:

```terraform
import {
  to = redshift_column_grant.events
  id = jsonencode({
    workgroup_name = "warehouse"
    database       = "admin"
    database_name  = "analytics"
    schema_name    = "reporting"
    object_name    = "events"
    grantee        = "analysts"
    grantee_type   = "ROLE"
  })
}
```

Alternatively, use `terraform import`:

```shell
terraform import redshift_column_grant.events \
  '{"workgroup_name":"warehouse","database":"admin","database_name":"analytics","schema_name":"reporting","object_name":"events","grantee":"analysts","grantee_type":"ROLE"}'
```
