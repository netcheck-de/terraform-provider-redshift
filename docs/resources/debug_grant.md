# redshift_debug_grant (Resource)

Grants `DEBUG` on one database in a warehouse with
[federated permissions](https://docs.aws.amazon.com/redshift/latest/dg/federated-permissions.html). Redshift redacts
sensitive values in the secure logging records of queries that read fine-grained access controlled data; `DEBUG` lets
the grantee see them unredacted. The grantee is a global identity, an Identity Center group, or the superusers of an
account. See AWS [GRANT DEBUG](https://docs.aws.amazon.com/redshift/latest/dg/r_GRANT.html#grant-debug-syntax),
[usage notes](https://docs.aws.amazon.com/redshift/latest/dg/r_GRANT-usage-notes.html#r_GRANT-usage-notes-debug), and
[REVOKE](https://docs.aws.amazon.com/redshift/latest/dg/r_REVOKE.html).

## SQL Statements

```sql
GRANT DEBUG ON DATABASE database TO ...;
REVOKE DEBUG ON DATABASE database FROM ...;
SHOW GRANTS ON DATABASE database;
SHOW GRANTS FOR ... FROM DATABASE database;
SHOW DATABASES LIKE 'database';
SELECT TRIM(auth_method) ... FROM sys_connection_log WHERE session_id = pg_backend_pid() ...;
```

## Example Usage

```terraform
# Remote USER/ROLE aliases require SQL-superuser access to a current-session IAM AssumeUser authentication event,
# plus SHOW DATABASES visibility. Password/local-secret sessions cannot verify remote DEBUG readback.
# An IAM user sees the unredacted secure logging records of its own queries on the database.
resource "redshift_debug_grant" "auditor" {
  database     = "sales_db@finance-catalog"
  grantee      = "IAM:sales_auditor"
  grantee_type = "USER"
}

# Every member of an Identity Center group sees the records of their own queries.
resource "redshift_debug_grant" "audit_team" {
  database     = "sales_db@finance-catalog"
  grantee      = "myidc:audit_team"
  grantee_type = "ROLE"
}

# Connect this resource's provider to the producer warehouse; remote ACCOUNT readback is unavailable.
# Every superuser of the producer account sees all records.
resource "redshift_debug_grant" "producer_admins" {
  database     = "sales_db"
  grantee      = "123456789012"
  grantee_type = "ACCOUNT"
}
```

## Schema

### Required

- `database` (String) Database with federated permissions that `DEBUG` applies to. `ACCOUNT` requires a producer-local name such as `sales_db` and a provider connected to that producer. Remote `USER`/`ROLE` aliases such as `sales_db@finance-catalog` require a SQL superuser, a verified `IAM AssumeUser` current-session authentication event in `SYS_CONNECTION_LOG`, and alias visibility in `SHOW DATABASES`. Password, unavailable, or unverified remote contexts are errors even if the alias is listed.
- `grantee` (String) Receiving identity: a global identity `<prefix>:<name>` (such as `IAM:sales_auditor` or `IAMR:audit_role`) for `USER`, an Identity Center group `<prefix>:<group>` for `ROLE`, or a 12-digit AWS account ID for `ACCOUNT`, which must own the producer.
- `grantee_type` (String) `USER` for a global identity (`TO "<prefix>:<name>"`), `ROLE` for an Identity Center group (`TO ROLE "<prefix>:<group>"`), or `ACCOUNT` for the superusers of an account (`TO ADMINS OF ACCOUNT '<account_id>'`). Accepted in any case; another case of the same keyword is recorded in place.

### Read-Only

- `id` (String) JSON import identity; independent of Data API execution history.
<!-- markdownlint-enable MD012 MD013 MD022 MD033 -->

`grantee_type` selects the grantee form:

| `grantee_type` | `grantee`                                       | Statement                             |
|----------------|-------------------------------------------------|---------------------------------------|
| `USER`         | global identity `<prefix>:<name>`               | `TO "<prefix>:<name>"`                |
| `ROLE`         | Identity Center group `<prefix>:<group>`        | `TO ROLE "<prefix>:<group>"`          |
| `ACCOUNT`      | 12-digit AWS account ID of the producer account | `TO ADMINS OF ACCOUNT '<account_id>'` |

The prefix of a global identity names its identity provider: `IAM` for an IAM user, `IAMR` for an IAM role, or the
Identity Center namespace for an Identity Center user. A `USER` or `ROLE` grantee without a prefix is rejected during
planning, because Redshift refuses `DEBUG` for local users, local groups, and `PUBLIC`. A global identity sees only
the records of its own queries, and so does each member of a group; account administrators see every record, also
when Redshift exports system tables to Amazon S3 Tables. `DEBUG` is prospective: it affects only records written
while it is granted.

## Lifecycle and Ownership

Only a superuser or the owner of the database can grant or revoke `DEBUG`, and only on a database in a warehouse with
federated permissions. Statements run in the provider's administration database and name the database, so a
cross-warehouse `USER` or `ROLE` name such as `sales_db@finance-catalog` does not require connecting to that database.
Before a remote GRANT or remote absence inference, the provider verifies the current session's authentication event
in `SYS_CONNECTION_LOG`, filtered by `session_id = pg_backend_pid()`, `user_name = current_user`, and
`event = 'authenticated'`, taking only the latest record. The exact supported result is `IAM AssumeUser`, verified
with IAM Data API sessions. That system view requires a SQL superuser. Password authentication, an unavailable or
ambiguous record, and other unverified authentication methods fail closed, even if `SHOW DATABASES` lists the alias.
A local-secret session can list the alias yet return no remote DEBUG rows for a grant that actually exists; alias
visibility, IAM-looking usernames, `SHOW GLOBAL IDENTITY`, and external user IDs alone are not sufficient proof.
No direct-TLS or Identity Center authentication-method spelling is guessed or accepted without evidence.

The provider also requires `SHOW DATABASES` to list the exact alias and proves the scoped grant read can run before
mutation. `ACCOUNT` must use a producer-local database name and a provider connected
to the warehouse hosting that database. No authoritative remote ACCOUNT read shape is available, so remote ACCOUNT
configuration, imported-state reads, and deletion are explicitly refused with instructions to use the producer.
Legacy remote ACCOUNT state is retained with an error: manage or revoke the actual grant through the producer-local
provider and explicitly migrate/import its local identity. Changing authentication must not silently relinquish a grant.
`DEBUG` is not part of
`GRANT ALL ON DATABASE` and never carries a grant option, so this resource owns exactly one grant and other database
privileges, managed by `redshift_object_grant` and `redshift_grant`, are unaffected. Deregistering the warehouse from
the AWS Glue Data Catalog keeps the grant without effect; dropping the database removes it. A query that joins several
databases with federated permissions needs `DEBUG` on each of them to be unredacted.

## Reconciliation

Refresh runs `SHOW GRANTS ON DATABASE` and looks for the `DEBUG` row whose `identity_type` is `global_user`,
`global_group`, or `admins_of_account` for `USER`, `ROLE`, or `ACCOUNT`, comparing `identity_name` without case. There
is no in-place SQL; every change replaces the grant: `REVOKE DEBUG` from the old grantee, `GRANT DEBUG` to the new
one, each followed by a `SHOW GRANTS` read that verifies it.

Remote `USER` and `ROLE` tuples instead use `SHOW GRANTS FOR ... FROM DATABASE "db@catalog"` as the primary read:
remote `SHOW GRANTS ON DATABASE` can return an empty result even while the grant exists. Only the matching database,
`DATABASE` object/scope, exact grantee name (case-insensitive), `DEBUG` privilege, and scoped `user` or `role` identity
type count. These scoped row types are normalized only for the corresponding remote USER/ROLE tuple; local matching
still requires the global identity types above. Every remote read proves authentication and alias visibility,
including Delete's pre-revoke and post-revoke checks.

| Change                                 | Result                                                                      |
|----------------------------------------|-----------------------------------------------------------------------------|
| `database`                             | replaces the grant: `DEBUG` is granted on one database per statement        |
| `grantee`                              | replaces the grant: the grantee is part of the grant                        |
| `grantee_type` set to another keyword  | replaces the grant: the grantee form and its catalog identity type change   |
| `grantee_type` spelled in another case | no SQL; the update checks that the grant still exists and records the value |

**Drift.** A `DEBUG` grant revoked outside Terraform is removed from state, and the next plan grants it again. When
`SHOW GRANTS` fails for a local name and `SHOW DATABASES` no longer lists the database, the database counts as dropped
and the grant is removed from state too. An unverified remote authentication context, an alias omitted by
`SHOW DATABASES`, a failed remote query, or a remote
ACCOUNT tuple always preserves state and reports an actionable error; none is treated as an absent grant or a reason
to silently skip revocation. Only a verified IAM remote USER/ROLE session with a visible alias and no matching scoped
grant row reports absence. If an
invisible alias was actually dropped, remove its obsolete grant from state explicitly. Other grants are never owned.

## Import

Use an `import` block with a JSON identity:

```terraform
import {
  to = redshift_debug_grant.auditor
  id = jsonencode({
    workgroup_name = "warehouse"
    database       = "sales_db@finance-catalog"
    grantee        = "IAM:sales_auditor"
    grantee_type   = "USER"
  })
}
```

The example binds a Serverless workgroup. Replace `workgroup_name` with `cluster_identifier` for a provisioned
cluster, or with `endpoint` (`host:port`) for a direct password connection; see
[connection methods](../guides/connection_methods.md#imports-and-transport-switching).

Alternatively, use `terraform import`:

```shell
terraform import redshift_debug_grant.auditor \
  '{"workgroup_name":"warehouse","database":"sales_db@finance-catalog","grantee":"IAM:sales_auditor","grantee_type":"USER"}'
```

The JSON identity's `database` is the database `DEBUG` applies to, and `grantee_type` is upper case.
