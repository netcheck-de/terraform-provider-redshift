# redshift_datashare_objects (Data Source)

Lists current producer datashare members in the selected database, including functions and objects added by bulk
statements or `INCLUDENEW`, without taking ownership. Omit `database` to use the provider database, and omit `datashare`
to observe every outbound share there. See AWS
[SVV_DATASHARE_OBJECTS](https://docs.aws.amazon.com/redshift/latest/dg/r_SVV_DATASHARE_OBJECTS.html).

## Example Usage

```terraform
data "redshift_datashare_objects" "example" {
  database  = "analytics"
  datashare = "reporting"

  # Optional: omit to observe schemas, relations, and routines together.
  object_type = "function"
}
```

## Membership and Ownership

The listing observes current membership, not the statements that established it. It cannot distinguish a member added
explicitly from one added by `ADD ALL TABLES IN SCHEMA`, `ADD ALL FUNCTIONS IN SCHEMA`, scoped grants, or `INCLUDENEW`.
An empty or absent share or producer database yields an empty list. Catalog permission and execution errors are errors,
not an empty result. Only rows visible to the connection identity are returned.

`object_name` is opaque catalog text. AWS documents schema-qualified names, but not how function overload signatures
are encoded in this column. The provider does not infer an overload identity or split names at periods.

### Exclusive bulk ownership versus snapshots

AWS [ALTER DATASHARE](https://docs.aws.amazon.com/redshift/latest/dg/r_ALTER_DATASHARE.html) expands `ALL TABLES` and
`ALL FUNCTIONS` over existing objects. These statements do not establish a persistent catalog tuple. `INCLUDENEW`
separately adds future tables, views, and SQL functions; disabling it does not remove existing members.

A resource must not execute `REMOVE ALL TABLES/FUNCTIONS IN SCHEMA` on destroy after recording only the members seen
at creation: that would also remove later explicit or automatically included members. Refreshing its recorded set to
every current member would silently adopt those members instead. Import cannot recover the original snapshot.

`redshift_datashare_membership` instead owns every member of one kind in the share/schema. It is incompatible with
explicit membership resources for that kind and with `include_new = true`. It compares current source objects and
current memberships, and repairs incomplete coverage in place. Destroy deliberately removes the entire current kind,
not a remembered creation-time set. No provider-wide coordinator is introduced.

`ADD FUNCTION schema.name(argtypes)` identifies an overload, but live Serverless verification found that
`SVV_DATASHARE_OBJECTS` and `DESC DATASHARE` report two identical `schema.name` rows when INTEGER and VARCHAR overloads
are both shared. Removing either leaves one indistinguishable row. `SHOW DATASHARES` exposes only share metadata.
A per-function membership resource remains deferred: a name-only existence check could report a different overload as
managed. The bulk FUNCTIONS owner can compare counts for all current overloads; it does not need to identify one
overload. This listing preserves duplicate raw rows without assigning signatures to them.
